## Reference applications

### Stremio

**Identification lives in distinct layers.** Core `src/models/meta_details.rs` holds addon resource requests; web `src/routes/MetaDetails/useMetaDetails.js:40` loads `meta` by type/ID. Those clients are not a general-purpose disk filename scanner. The separate local addon `lib/indexer.js:93–127` feeds the full file path/length to `video-name-parser` with strict/fromInside options, then gives parsed name/year/type to `name-to-imdb` (whose built-in queue is noted). Season/episode coordinates are retained. Direct video files without an IMDb result are omitted (`:32–40`); torrent entries can retain generic metadata. Do not interpret its apparently clean library as proof that every file matched.

**Metadata/art.** `lib/mapEntryToMeta.js:7–51` selects the first IMDb-bearing file, establishes Metahub poster/background/logo URLs from that ID, then requests Cinemeta metadata; failure keeps the generic/ID-derived artwork rather than discarding the whole item. It assumes one IMDb title per torrent. `lib/metaHandler.js:25–33` checks metadata storage before rebuilding. Core `src/models/common/resource_loadable.rs:103–133` distinguishes loading/ready/error and `ResourcesAction` distinguishes ordinary from forced requests. This is request reuse, not evidence for a particular disk TTL.

**Loading/fallback/correction.** Web `src/routes/MetaDetails/MetaDetails.js:220` renders `MetaPreview.Placeholder` while metadata is loading; `MetaPreview.js:104` retains a text name when no logo draws, and `MetaItem.js:71` has an artwork placeholder icon. The inspected local-indexing path has no NFO/embedded-tag reader or Plex-style manual fix-match flow. ISO/BDMV handling, parser dependency internals, exact confidence thresholds, remote retry/backoff and local metadata TTL remain unestablished. Cinemeta/addon resources are demonstrated; a fixed global TMDB→TVDB→OMDb→Fanart chain is not.

### Jellyfin

**Parsing and context.** `Emby.Naming/Video/VideoResolver.cs:42–104` validates extensions, cleans dates/names and records extra/3D/container information. `Emby.Naming/Common/NamingOptions.cs` supplies configurable episode/extra/cleaning rules; `Emby.Naming/TV/EpisodeResolver.cs` resolves episode coordinates. `MediaBrowser.Controller/Library/ItemResolveArgs.cs:44–120` carries children, file/directory and parent context into item resolution. `MovieResolver.cs:372–402` extracts provider IDs from paths; `:414–540` recognizes DVD/Blu-ray/multidisc folders. Library type and folder context matter. Naming guidance covers year/IDs, versions and disc folders; folder discs have restrictions on versions/parts/external tracks. [Movies](https://jellyfin.org/docs/general/server/media/movies/).

**Providers and matching.** `TmdbMovieProvider.cs:55–118,152–193` uses TMDB IDs directly, converts IMDb IDs through TMDB's external-ID find, and searches only when needed. `TmdbUtils.cs:188–255` scores exact normalized localized/original title 8, whole-word title prefix 4, year within ±1 adds 2; ties preserve result order. There is no minimum rejection threshold there: an all-zero search can still return its first result. This is ranking evidence, not a confidence model to copy. Default providers include TMDB/OMDb/local NFO; TVDB, Fanart.tv and AniDB are plugins, with library configuration controlling participation. [Metadata providers](https://jellyfin.org/docs/general/server/metadata/).

**Sidecars, cache, repair.** `MetadataService.cs:805–885` processes local metadata before the remote enrichment stage. `BaseNfoParser.cs` reads provider IDs, titles and artwork references. NFO can identify titles by provider ID/link and takes precedence over remote metadata; it also supports local/remote artwork references. [NFO guide](https://jellyfin.org/docs/general/server/metadata/nfo/). `TmdbClientManager.cs:26,442–463` caches nonempty search results by title/year/language (one-hour manager cache), while `MetadataService.cs:95–104` supports library refresh intervals. No uniform HTTP retry/backoff was established in these files. Web `components/itemidentifier/itemidentifier.js:42–70,259–279` gathers name/year/provider IDs and applies a selected search result, with an option to replace images. `components/loading/loading.ts:17–24` owns a show/hide loading component; identifier search uses it. Exact detail-page loading visuals and embedded-video-tag precedence were not runtime-verified. Local images are handled separately by `MediaBrowser.LocalMetadata/Images/LocalImageProvider.cs`; no-art does not require accepting a wrong title.

## Part B: double spinner and slow title opening

### What source proves, and what it does not

- `AppleRemoteImage.swift:65–77` paints a loading fill rather than a `ProgressView`; build 18 also had that behavior. A poster spinner layered with a hero spinner is not supported by this source.
- `AppleDiscoverView.swift:9564–9584,9667–9678` has a busy primary-button indicator. Series shelves have separate loading state (`:4667` on tvOS; iPhone uses redacted episode rows). Download/trailer controls have their own indicators (`AppleTitlePageSections.swift:543–554,768–781`). Multiple indicators in different controls can coexist; that does not establish two centered circles over one another.
- The known September playback overlap is already addressed in both versions: `ApplePlaybackSpinnerPolicy.swift:14–23` allows the tvOS screen indicator only before a first route; `AppleMediaPlaybackView.swift:211–226,292–303,320–324` mounts the transport only for surface and latches `hasRouted`. Its policy is unchanged against `dc5e24e`. Do not propose that old fix as a newly discovered cause.
- **Remaining plausible overlap:** `AppleMediaPlaybackView.swift:198–205` mounts `platformPlayer` for every route except surface, including `.none`; `:885–913` installs the stock controller. `ApplePlayerHost.swift:381–411` binds the engine's AVPlayer without checking the presentation route. On tvOS, the independent `.none` busy screen spinner is therefore laid over a mounted AVKit controller. If AVKit starts its own waiting UI before the coordinator publishes/latches `.avPlayer`, there can be two indicators. Mounting the stock visual controller only for `.avPlayer` would remove this opportunity. The existence of a mounted host is observed; AVKit drawing its indicator during that interval is **not runtime-proven**. This hypothesis cannot explain a plain iPhone detail open, since the outer screen spinner is tvOS-only.
- **Diagnosis status:** the owner's exact build-18 stacked circles have not been reproduced in this pass. No screenshot/frame capture of that state is available. Confirm title click versus Play, platform, `.none`→`.avPlayer` order, retries and noncanonical IDs before selecting a spinner fix. Logs of loading requests alone cannot count visible indicators.

### Concrete causes of slow filling

1. **Intentional art delay:** `AppleTitlePageSlotArt.swift:17,27–28`; `AppleDiscoverView.swift:4815–4824,4837–4854,9357` holds phone slot art black until details is nonnil or the 1.5-second deadline. Already available/cached catalog art is not displayed in that interval; a nil metadata answer is not distinguished from unanswered. Proposed change: seed the final slot promptly from suitable catalog/cached art; represent answered-empty separately and keep a stable fallback. This is a source-proven delay, not measured CPU cost.
2. **Noncanonical identity gates later detail requests:** `AppleStremioMetadataClient.swift:649–670` walks sources sequentially; `AppleDiscoverView.swift:7158–7184` starts episode/enrichment lookups after that identity outcome. Canonical IMDb items skip this phase. Preview assets also walk sources serially (`AppleStremioMetadataClient.swift:673–728`), with individual network requests allowing 15 seconds. Proposed change: resolve known provider IDs directly and coalesce/cache bounded identity lookup, then let independent metadata/art/episodes arrive progressively.
3. **Metadata merge is not first usable answer:** `AppleMetadataClient.swift:856–926` launches providers concurrently but collects all bounded outcomes before merging; the default request deadline is one second. Cancellation must cooperate for that timer to be a wall-clock bound. This path is already faster than serial requests; do not confuse it with the separate serial library matcher. Proposed change: publish useful cached/early fields without waiting to finalize the merge, while preserving provider priority/manual corrections.
4. **Tail work delays “done,” not necessarily the first frame:** `AppleDiscoverView.swift:7206–7222` awaits watch-provider enrichment before optional artwork fallback; `:3677–3679` marks done only after `prepare` returns. Series outcome handling also awaits progress/offline bookkeeping before the next completed outcome is consumed (`:7187–7189`). Move optional tail work off the artwork/first-use path. Catalog text can already appear before enriched details.
5. **Existing instrumentation limits:** `AppleDetailFillTimeline.swift:56–83` starts at the title's task and immediately marks paint; it is not a compositor first-frame measurement or tap→paint timestamp. Historical comments mention 10–18-second fills, but those are not a new baseline. Measure navigation tap, first composited frame, first usable actions and separate metadata/art milestones; do not call “done” the time when the user first sees the page.
