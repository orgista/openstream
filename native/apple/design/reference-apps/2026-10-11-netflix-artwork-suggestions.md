# Netflix artwork, icons and suggestions — Worker B, 2026-10-11

## Summary

This is a polish investigation, not a redesign. Netflix's shipped Android phone client requests artwork by treatment and context, retains artwork identity alongside title identity, renders several distinct row types, and carries row/item positions into tracking. It consumes supplied recommendation lists; this inspection does **not** recover Netflix's server ranking algorithm, its weights, or its global duplicate policy. The TV APK's main UI remains behind the native library boundary; phone findings are not tvOS measurements.

OpenStream's best immediate changes are to connect the signals its existing rankers already accept, remove duplicate candidates before ranking, and resolve artwork for the required context. In particular, Discover sends **empty genres for both history and candidates**, derives history only from Continue Watching, and can emit the same digest more than once. These are more consequential than copying Netflix's glyph appearance. Preserve titles under posters, progress on artwork, accent #FF3366, Apple system chrome, textless backdrops, the approved billboard fade, and no explainer text. Trailers remain tabled.

The ranked proposals below are independently designed OpenStream behavior. No Netflix implementation, vector paths, artwork, or assets were added to the app. Only this report was written; no builds, APK execution, installs, simulators, emulators, uploads or commits.

### 7. Current OpenStream ranking gaps

Paths below are relative to `native/apple/`; every shortened Swift filename refers to `Sources/OpenStreamApple/<filename>`. Source inspection was read-only.

- **Inactive genre affinity:** `AppleDiscoverView.swift:645` and `:667` supply empty genres to history and candidates. `AppleRecommendationRanker.swift:88` only computes affinity when candidate genres are nonempty. With ordinary unrated titles, scores therefore tie and resume/year/completeness/id dominate. This is a source deduction, not a runtime test.
- **Narrow history and wrong recency source:** Discover uses only its local Continue Watching list (`:645`) and `record.lastVerified` (`:649`), rather than playback `updatedAt` or completed-watch timestamps. The viewing signal's `completed` field exists but the ranker never reads it. Completed titles persist in `ApplePlaybackStore.swift:85`, `:136`, `:226`; Top Picks uses completion only to demote candidates at tied score, not to learn taste.
- **Duplicates:** candidate collection keys by source record ID (`AppleDiscoverView.swift:654`), then maps each to a playback digest (`:668`). `byDigest` retains one representative but `rankable` still includes every source instance. Rank output maps repeated digests back to the same representative (`:686`). Dictionary iteration also makes first-representative choice unstable. Canonical identity and source choice must be separate.
- **Rating edge case:** `AppleRecommendationRanker.swift:84` awards 100 whenever a rating exists other than doubleUp; `.none` therefore receives a boost through the public rank API. Store reads exclude `.none`, so the normal Discover caller mitigates this; pure ranker behavior remains surprising. Up/doubleUp get large direct boosts and multipliers, while dislikes exclude the title but do not influence related-title taste.
- **Recommendation/resume conflation:** `AppleRecommendationRanker.swift:115` always puts resumable titles first; CW already owns that job. Hero candidates begin with CW, then picks, then server shelves and only the first eligible catalog (`AppleDiscoverView.swift:526`). Five resumable titles with art can occupy the whole rotation. This is current owner-approved precedence, not authority to change it silently; any novelty quota must preserve the lead resume behavior unless the owner changes that decision.
- **Similar-title quality:** `AppleSimilarTitleRanker.swift:144` uses same-type genre/keyword/people/year/rating similarity and canonical dedup; useful existing work. Its diversity step at `:194` penalizes all later titles whose primary genre appears in the original top three, then resorts once. This is not iterative selected-set diversification. Missing relevance can still leave a positive year/rating prior (`:180`, `:211`). Detail supplies only `relatedItems` (`AppleDiscoverView.swift:5628`); the inspected call sites commonly request these for one source (`:931`, `:1250`).
- **TMDB relations are potential data, not proven wired data:** the assignment names recommendations/similar metadata as available, but the inspected `AppleTMDBDetails` (`AppleMetadataClient.swift:22`) has no relationship arrays, and bounded source search found no recommendations/similar endpoint handling in `AppleTMDBClient`. The current detail refresh explicitly makes no network call (`AppleDiscoverView.swift:5624`). Use already cached relation IDs if another provider supplies them; otherwise relation acquisition is a separate implementation dependency. Do not claim this signal is already feeding either ranker.
- **Taste scope:** `AppleTitleRatingStore.swift:18` and `ApplePlaybackStore.swift:72` use global default keys within the injected defaults store. No viewer namespace enters either inspected ranker. This does not justify adding a whole profiles product in a polish pass; ensure any existing per-viewer storage/caches stay isolated, and otherwise describe the present taste scope honestly.

### Concrete on-device suggestion approach

This is an implementation proposal using local evidence, not a reconstruction of Netflix's model. Start with ranks 1–4; they repair existing input/identity behavior before adding a new feed.

1. **Snapshot and normalize:** capture accessible catalogs/library/server references, title kind, canonical IDs, known metadata, progress/completed timestamps, explicit ratings and My List state once per revision. Keep source instance references for opening content; titles identify preference, sources identify playback routes. Existing stores know progress and completed state, not every historical play session or impression.
2. **Construct candidate sets:** separate resumable titles, unseen recommendation candidates and authoritative ranked/popular/provider rows. Use local genres/synopsis/people plus relation IDs already cached or explicitly acquired under metadata settings. Exclude live channels from title recommendations. Treat provider row order as a limited prior; release year is not popularity and Netflix rank is only meaningful in the real rank feed.
3. **Build taste:** retain the existing 14-day recency decay as a testable initial parameter, rather than attributing it to Netflix. Completion/meaningful progress, explicit thumbs and saved-list membership contribute bounded evidence. Cap contribution per show so many episode progress updates cannot dominate taste. A resumed title belongs in CW; removing it from CW is not the same as dislike. A saved title may be intent without viewing satisfaction.
4. **Score relevant unseen candidates:** combine normalized content affinity to strong history/liked seeds, available relation proximity, bounded metadata/rating priors and freshness of truly newly added local content. Require at least one relevant content/relation signal for personalized claims; year/IMDb rating alone is insufficient. Return neutral fallback catalogs if no usable signals exist. Coefficients are OpenStream parameters to evaluate, not Netflix-derived numbers.
5. **Compose and diversify:** preserve CW, real Top 10 rank and custom row order. Top Picks and any compact seed/genre rows use stable per-title ties and incremental overlap penalties. Explain provenance internally; normal UI remains just approved row labels and card titles. Keep the lead resume hero and cap any novelty experiment to the remaining candidate slots.
6. **Cache and invalidate:** ranking runs off the view-render path against the snapshot; key it by source/catalog/metadata and taste revisions. Changing a rating, watching/completing a title, losing a source or updating metadata invalidates the appropriate result. Missing metadata yields graceful neutral candidates rather than blocking visible shelves.

Do not treat passive scroll/focus as likes or claim impression learning exists today. If exposure fatigue is later wanted, it needs an explicit new bounded local visibility record, offscreen filtering, accessibility-aware behavior and retention policy; it is not one of our current signals and is not required for the initial polish. No remote recommendation telemetry is proposed.

Future validation should cover duplicate titles across sources, `.none` neutrality, completed-history recency, many episodes of one show, unknown metadata, missing backdrop with an existing poster, art-load failure, inaccessible relation candidates, rating/source changes, sparse cold start, and preservation of explicit row order. Tests and visual Apple-platform validation belong to a later implementation task, not this report-only pass.
